    Design

    (I) - What is the difference between Ui and UX?

    UI, or user interface, refers to the elements the player uses to interact with the game, whether they are controls, HUD (heads up display) elements that communicate information about the game, menu buttons, or in text-based/non-visual games, the text interface or screen readers. GUI refers to graphical elements specifically, though most UI is graphical these days. UX is the User Experience, and UI contributes to that experience. It's designing the overall experience a user will have, thinking about how they interact with the UI and the gameplay, and what it feels like to play the game in general.

    While an example of designing UI would be crafting the weapons menu and hotkeys and their appearance/placement, designing the UX would be considering where those hotkeys should be so it feels natural to switch weapons, and making sure the GUI elements don't misdirect the user to accidentally unequip or sell their gear, etc. There is a lot of overlap, and you often have to think about UX a lot while designing UI, but they're not completely the same thing in the way rectangles and squares are overlapping categories, not identical.

    (II) - What are the main 'UI Design Principles'?

    Opinions differ on what the "main" design principles for UI are, and a lot of them overlap somewhat, but here are some I'd consider:

    Clarity: This is about making the most important information as clear as possible so that basic actions don't become confusing unnecessarily. If a player will need to access their healing items often, it should be as easy as possible to see and understand where they are, the amount, and how to use them. An exit button for a menu that lacks clarity might blend in by being a very similar colour as the background, be in a strange place, or have a symbol that makes it look like a volume button instead.

    Simplicity: Simplicity is similar to clarity, but is more about making sure the UI doesn't get in the way of the UX. It isn't about removing detail or style, but making sure the complexity of the navigation and layout is proportional to how the player will be using it, or just generally avoiding letting the UI obscure its own function/the game it's for. An overcomplicated UI might have the HUD covering important sightlines with less vital information/decorations, or have 3 nested menus to get to 1 commonly used feature, or have the visual hierarchy in a reverse order where the most important information is small or hidden. A sufficiently simple UI will almost disappear to the user, in the sense that it won't feel like an obstacle to gameplay. The amount and ways this principle gets applied will of course vary depending on the project. Even a game like Persona 5, despite being a ridiculously complex UI style wise (sometimes to its own detriment), still has elements of simplicity, but it's not as overt and mostly shows itself in the overall UI organisation and the visual hierarchy in each screen.

    Consistency: It's easy to forget about consistency when it's done well, but it's always something to keep in mind. Consistency is just about keeping the rules and style for your UI the same across the whole game. You can use a style guide to do this, and some game engines have the ability to set themes for UI, like Godot, where you can design elements in a separate tab, view previews of them, and have that style applied to every child node of where you set the theme. A consistent UI helps with clarity/legibility as well as simplicity insofar as it prevents having a clashing distracting UI and having a set of rules lets you more easily focus on organising things well. You can of course break the rules sometimes, like for an area or story beat where the point is to break consistency for a moment, and some degree of inconsistency can be a key part of a game's style, but it should always be considered to some extent and can solve a lot of common UI issues. Consistency also applies to controls, for example pressing A in the inventory menu shouldn't close or go back if A is also the button to confirm or equip items elsewhere. Having a set confirm/positive button and a cancel/negative button is just overall good UX design, and that's an idea that applies to making all parts of your UX/UI consistent.

    Feedback: Feedback is just ensuring that actions/interactions have some kind of feedback to show that the game recognises the input. This could be using different sprites for a button that's being hovered over or pressed, making the controller vibrate on a successful parry, or through tactile audio like a paper folding noise when opening/closing the map or a building SFX to communicate the charging up of a big skill. Hollow Knight is a perfect example of this; along with both of those last examples, the feedback for when the player gets hit is intense, outright freezing the game for a moment and having the whole screen react, and finding hidden entrances can be as natural as noticing loose stones rattle and shake beneath you while walking. When entering a secret area, a curious sounding tone plays, giving a little bit of positive feedback for discovering that secret instead of letting it feel like any other room. Simple bits of feedback like that can make a surprising impact on how the player feels about and plays your game.

    Accessibility: This is often overlooked, but is incredibly important. Accessibility is about ensuring your game is playable to as much of your audience as possible, even if they have some visual/auditory/motor/cognitive disabilities or other needs. UI wise, this can look like closed captions/subtitles and some visual options for them, colourblind view options (on top of designing around that consideration, because not everyone knows they're colourblind, and keeping colour values and contrast in mind is already something you should be doing), text/UI scaling, dyslexic font options, motion blur toggles, or button remapping/alternative controller support. Minecraft has a quite nice implementation of this in some aspects, featuring a subtitle system that displays the audible sounds on the side alongside what direction they're coming from, with the text for each sound fading out once it's done playing. It's a good example of how accessibility features can mesh smoothly with the game, and can benefit everyone, as even players who don't struggle with hearing use the feature either for fun or so they don't miss something while chatting with their friends in game.

    Some other factors like visual hierarchy and reducing cognitive load I only slightly touched on here, but they're really just features of the rest of these principles when everything is executed well. Like many other principles in creative work (the 12 principles of animation for instance), it's not a hard rule, only something to always consider while designing your game.

    (III) - What is interactivity in regards to UI design in both games and apps?

    Interactivity feels somewhat self-explanatory, but if I had to word it any more clearly, I'd say it's about the 'conversation' between the player/user and the software. The user wants something from the software, and interactivity is about the way they can do so and how. This is done through interactive elements like buttons or sliders or interactive design like the game world and control systems, and the overall level of interactivity is determined by all of those elements working together. Some level of interactivity is necessary for function, but individual games or apps will have their own different requirements for it depending on their genre or purpose. You'll want everything to be as interactive as possible in a physics sandbox game, while a rhythm game might be a little more restrained, and a visual novel will want its interactivity to be a very particular way in order to serve the story. A similar difference can be found in apps, where a firewall app only needs the basic interactivity to function while a music player will want an awful lot more, and more carefully implemented to not blow anyone's ears out.

    (IV) - What are 'Style Guides' in UI? And how are they useful when building an overall look and feel of a game?

    A style guide is almost like a GDD (games design document) for the UI/UX of a game. It includes things like the particular fonts, colours, UI shapes, and the rules surrounding when, where and how they all get used. They're useful in much the same way a GDD is, in that they give the team/dev(s) some solid reference to work based on and a clear final visual goal for the UI, which brings with it consistency. By taking the mental load of deciding colours and button shapes and the like from UI designers, the whole process becomes simpler, which tends to result in more room to think about the other factors that make good UI/UX and focus on making the particular parts they're working on as functional and elegant as they can be.
